# redis-aws

Desired state for one [Redis](https://redis.io) 7.2 server on one AWS EC2
instance in `us-east-1a`, using the
[`redis`](https://github.com/getcolors/redis) Package Skill: one Docker
Compose service with `noeviction` and an append-only file, published on
loopback only, reached over an SSH tunnel, with RDB backup sets in a
deployment-owned S3 bucket and a rehearsed restore.

This repository holds `colors.yml`, the installed launchers, `.envrc`, and
`devenv.nix`. Everything else is generated (`.colors/`) or secret
(`.envrc.private`).

The launcher payload is installed after the package's tri-colour release is
pinned. Until then the repository is desired state alone and no verb runs.

## Use

Choose `./green` (Babashka), `./red` (Bun), or `./blue` (uv/Python). All
three read the same `colors.yml`, write the same SSH alias, and share the
same OpenTofu state. Run one lifecycle operation at a time. Replace `green`
below with `red` or `blue` to use that runtime.

```sh
direnv allow                 # once, after the toolchain is installed
./green build                # render .colors/redis-aws/ with no credentials
./green create --dry-run     # walk the workflow, skip every side effect
./green create               # converge for real
./green describe             # the host's last monitor result, over SSH
./green rehearse             # fresh set, restore it into a scratch instance, read back
```

## What create owns

- One `t3.small` instance (Ubuntu 24.04, 20 GiB root volume) in a dedicated
  VPC and subnet, with a security group that opens 22 alone.
- The machine keypair `~/.ssh/redis-aws`, generated by the package (keygen
  mode).
- The OpenTofu state bucket `redis-aws-state-251213589273-us-east-1`, created
  by the library's managed backend.
- The backup bucket `redis-aws-backup-251213589273-us-east-1`, created by the
  package's storage stage.

Neither bucket exists before the first create. Both are removed by delete.

## Connecting

```sh
ssh -L 6379:127.0.0.1:6379 redis-aws
REDISCLI_AUTH=$(ssh redis-aws cat /etc/redis/secrets/password) redis-cli -p 6379
ssh redis-aws redis-status
```

The password is generated on the server and exists nowhere else. There is no
DNS record and no public Redis port.

## Credentials

One pair, in the gitignored `.envrc.private`: `COLORS_PAR_AWS_ACCESS_KEY_ID`
and `COLORS_PAR_AWS_SECRET_ACCESS_KEY`. `.envrc` maps them onto
`AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY` and sets
`AWS_DEFAULT_REGION=us-east-1`, so the compute provider, the state backend
and the storage stage all read the ambient AWS credential chain. Load
`.envrc` before any command that needs credentials. Never export
`COLORS_PAR_PROFILE`.

## Recovery

| Failure | Recovers from | RPO |
|---|---|---|
| a Redis restart | the append-only file (proven on every converge) | 1 s or less |
| the host | the newest completed set under `redis-aws/redis/` in the backup bucket | 6 h |

`./green rehearse` proves the path and writes
`redis-aws/.colors-recovery-verified` in the backup bucket.

## Updating the launchers

The root `./green`, `./red` and `./blue` are copies of
`.agents/skills/package-redis-<colour>/<colour>`, not symlinks.
`npx skills update -p` rewrites the payload and leaves the root files alone,
so copy them again after every update:

```sh
npx skills update -p
cp .agents/skills/package-redis-green/green green
cp .agents/skills/package-redis-red/red red
cp .agents/skills/package-redis-blue/blue blue
```

## Deleting

```sh
COLORS_PAR_COMPUTE_PREVENT_DESTROY=false ./green delete
```

Removes the instance, the security group, the VPC and subnet, the SSH config
block, the machine keypair, and both S3 buckets with everything in them. The
backup sets do not survive a delete; copy anything you need out of the backup
bucket first.
