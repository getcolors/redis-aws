the green launcher of the `redis` Package Skill. The whole lifecycle ran for
real: three converges, describe, one recovery rehearsal, describe again, a
refused delete, an authorized delete, and a repeat delete. The deployment is

each was fixed at the source, tested, pushed, pinned, and the payload
refreshed before the verb was re-run. The last live-verified green pin is
`ffb0777` (`getcolors/redis` main, pinned by `7ce215e`).

## What each gate proved

- **Acceptance (every passing create).** The tunnel through the generated
  alias round-trips with the generated password, an anonymous `PING` and a
  wrong password are refused, and `54.227.190.72:6379` does not answer: the
  bounded probe timed out (exit 124) while port 22 opened
  (`evidence/public-port-probe-1.txt`). On the host the kernel lists exactly
  `127.0.0.1:6379`.
- **First backup set.** Each converge left a completed set under
  `redis-aws/redis/<stamp>/` — `dump.rdb`, `manifest.txt`, and a 16-byte
  `.complete` written last. Read back with the AWS CLI:
  `evidence/backup-sets-after-create-1.txt`. `redis-status` over the alias
  lists the completed sets and the healthy monitor result.
- **Idempotence.** Instance, key pair, volume, subnet and launch time are
  identical across all runs (`evidence/compute-identity-across-runs.txt`).
  The container's `CreatedAt` (03:49:09Z) never changed across three
  converges while `StartedAt` moved each time — the smoke gate's restart,
  by design (`container-after-create-{1,2,3}.txt`). `~/.ssh/config` was not
  rewritten by run 2 (`ssh-config-after-create-2.txt`). The storage stage
  plans `No changes.` after run 3 (`tofu-plan-storage-after-create-3.txt`).
  The compute stages could not be planned from `.colors/`: colors-compute
  runs tofu in a private working directory it removes, and the tree under
  `.colors/redis-aws/redis-infrastructure/` is the build-time render with
  the placeholder public key, so a plan there proposes replacing the key
  pair and is not evidence (`tofu-plan-compute-after-create-2.txt` records
  that dead end; the `.terraform/` it created was removed).
- **Rehearsal.** A fresh set `20260911T041136Z` (288 bytes, 2 keys), the
  restore into a scratch instance, and the marker
  `redis-aws/.colors-recovery-verified` = `redis-aws set=20260911T041136Z
  at=20260911T041148Z` read back with the AWS CLI (50 bytes, AES256):
  `evidence/recovery-marker-after-rehearse-1.txt`,
  `redis-status-after-rehearse-1.txt`.
- **Guard.** A plain `delete` exits 2 at the start step before any provider
  or state work; the instance was still running afterwards.
- **Delete.** Instance terminated; VPC, subnet, internet gateway, security

## Bugs found and fixed

All four are in `getcolors/redis`; each fix carries a unit test, passed
`bb test`, `bb golden`, `bb syntax`, `scripts/launcher.sh` and
`scripts/parity.sh` (the red and blue suites too once those ports landed on
main during this run), and was pinned with `bb pin`.

1. **Storage stage: empty state not recognised under OpenTofu 1.12**
   (`7e51e2d`, pin `1b2befe`). The ownership preflight treated `tofu state
   list` on a stage with no state as empty only when stderr carried
   `No state file was found!`. 1.12.5 prints `Error: No state file was
   found` (coloured unless `-no-color`), so the check threw and the create
   failed with "managed S3 storage failed" after the instance existed.
   neon-multi-node-aws's `devenv.lock` had pinned 1.11.5 and never met it.
   Fix: `-no-color`, match the shared phrase through a tested
   `empty-state?` predicate; anything else still fails closed.
2. **Workstation reads assumed root** (`f51654e`, pin `fe46c11`). The AMI
   logs in as `ubuntu`; Vultr and DigitalOcean images as root. The
   acceptance's `ssh <alias> cat /etc/redis/secrets/password` was refused
   ("could not read the generated Redis password over ssh"), and the
   installed `redis-status` could not read `/etc/colors/backup-r2.env` or
   the Docker socket. Fix: the password read falls back to `sudo -n cat`,
   `redis-status` re-executes itself under `sudo -n` when not root, and the
   documented one-liner reads with `sudo -n cat` (works as root too).
   Goldens: two hunks in `redis-status.sh`, all six fixtures. This
   deployment's README, CLAUDE.md and index.html were updated to match.
3. **Perpetual drift in the encryption rule** (`dccd696`, pin `778c3d1`).
   After a converge the storage stage still planned one in-place update:
   AWS reports `blocked_encryption_types = ["SSE-C"]` and
   `bucket_key_enabled = false` on the new bucket and the template declared
   neither, so provider 6.31 rewrote the rule every apply. Fix: declare
   both, as `clickhouse` already does (`18ea94a`). Green owns the template;
   the red and blue resource trees are the byte-identical copies parity
   enforces. Golden: one hunk in the `s3/redis-aws-fixture` storage stage.
4. **Delete asked for the managed pair before reading it** (`ffb0777`, pin
   `7ce215e`). The cleanup play ran with the credentials flag, so
   `play-env` demanded the storage pair, but on the delete DAG the storage
   stage runs after the play (the bucket outlives the machine) and nothing
   had read it: "managed storage credentials unavailable", nothing
   destroyed. The play only runs `docker compose down`. Fix: run it without
   the pair, in all three colours (red `src/tools.ts`, blue
   `tools.py` carried the same flag), each with a test.

The payload was refreshed after every pin (`npx skills update -p`, root
launcher re-copied and diffed against the payload): commits `87a2184`,
`85be413`, `8b52dea`, `3b57d03`. Only the green payload is installed here;
the red and blue payloads exist on main since `daa6811` and were not
installed or live-run from this deployment.

## Oddities worth knowing

- The very first create failed after creating the instance, and every later
  create adopted it cleanly: the compute library's ownership coordination
  did its job through three package-side failures.
- The launcher's create log ends at the failing step's message with no tool
  output; the storage exception is swallowed into one line. Reproduce by
  hand in `.colors/<profile>/redis-storage` (`tofu state list`, `head-bucket`).
- `describe` reads `/var/lib/colors/redis-monitor.json`, which is 0644, so
  it never needed sudo; only the password file and the status helper did.
- AWS creates a default security group with every VPC (self-referential
  ingress, not attached to the instance); it appears in a by-VPC listing and
  vanished with the VPC.
- `evidence/` holds no credential: `evidence/credential-scan.txt`. One tofu
  plan echoed the storage user's access key **id**; it is redacted, and the
  key was destroyed with the user.
